# EDGEbuilder: notes for Claude sessions

EDGEbuilder is a world builder for Cyberpunk 2077 that runs as a REDnode package: pick an asset from the game's own files, drop it into the live game, position it, arrange a scene, bake it into a streaming sector. Read [docs/design.md](docs/design.md) first: the behaviours, the two halves, the pieces, what it needs from the other repos, and the roadmap B0 to B7.

## Picking this up on another machine

The repo is the whole hand-off: there is no state outside it except the player's data folder in the game. Start with this file, then docs/design.md, docs/scene.md and docs/b1-test.md. Sibling checkouts of REDnode (for the SDK source and the mock host), REDbridge (the bridge, 0.6.0 or later) and EDGEdeck make development easier but are not required to build: `npm install`, `npm run build`, `npm run smoke`. With Electron in the REDnode checkout (`node node_modules/electron/install.js` there once), run the host from `<REDnode>/packages/overlay`: `node start.js --render=cpu "--apps-dir=<REDnode>/packages/overlay/apps;<this repo>" --apps=edgebuilder "--data-dir=<scratch folder>"`. `--apps-dir` takes folders whose subfolders are packages, so it is this repo's root, not `edgebuilder/`. Put `{"bridgePath": ..., "gameDir": ...}` in `<scratch folder>/packages/edgebuilder/settings.json` first. Look at the page with the kernel MCP server's `window_image` tool (id `edgebuilder`; token in `<scratch folder>/settings.json`); it works off-screen with `--render=cpu`, not in `--window` mode. To drive the page, start `node_modules/electron/dist/electron.exe --remote-debugging-port=9223 . <same arguments>` from `packages/overlay` (the switch must come before the app path) and evaluate scripts in the page through the DevTools protocol on 127.0.0.1:9223. Done on 2026-10-13: see the B1 test page's results.

- **Asking the other repos for something:** open a GitHub issue in that repo labelled `request` with "From", "Need" and "Shape that would work" (REDnode, REDbridge and REDcode have the label and a one-line pointer in their CLAUDE.md). Link the issue from the design. REDnode #4 `kernel.bridge()` and #5 manifest `requires` shipped in REDnode 0.17.0 and EDGEbuilder uses both. Open ones that matter here: REDcode #2, the project half, for B4 and B7.
- **What the World Builder study found** is in docs/study.md: behaviours, object kinds and the game systems a world builder touches, for designing B2 to B6 without reading that mod again.

## Clean room

The idea comes from World Builder by keanuWheeze (Nexus 20660), a CET mod whose license reserves its code, forks and competing versions. The owner's rule (2026-10-13): study it to understand functionality and which game systems it uses, then write our own from scratch. **Never copy** its Lua, classes, file formats, data lists (its path lists are extracted game data) or archive assets. Design from behaviours and the game API; when a feature looks like it is drifting into World Builder's shapes, stop and redesign.

## Conventions

- **Commits:** commit straight to `main` and push, in small logical commits. Agree the plan in chat first. A PR only for large or risky changes, and ask before opening one.
- **Git identity:** per repo, `CyberbuildsAI` with the GitHub no-reply email. Never change the global identity.
- **Never commit game files** or data extracted from them: archives, meshes, entities, DLLs, the asset index, scenes with the owner's paths. `.gitignore` covers the common cases. The one shipped archive, EDGEbuilder's empty entity, is authored as JSON in this repo and built by REDbridge; the built `.archive` is never committed.
- **House style:** the README with the HUD banner, badges and a status callout; `docs/` rendered by Jekyll with the HUD layout and deployed by `.github/workflows/pages.yml` (Settings > Pages > Source must be GitHub Actions); `tools/brand/` generates the images (`.\tools\brand\render.ps1`, needs Chrome or Edge; `python -I tools/brand/badges.py docs/assets/brand/badges` for the badges alone). REDnode's CLAUDE.md is the canonical source of these idioms.
- **Writing style:** plain, short sentences, tables for comparisons. The behaviours are Browse, Drop, Position, Arrange, Bake, Return; use those words. REDnode's terms: package, overlay app, Node mod, the host, the plugin, `api`.
- **Package layout:** `edgebuilder/` is what deploys; `src/` is TypeScript built into it. `tools/deploy.ps1` mirrors `edgebuilder/` into `<game>\red4ext\plugins\REDnode\apps\edgebuilder` for development (REDnode deployed first, game closed). Players install it with EDGEdeck (0.20.0 and later know the `rednode` kind): add the release zip (`npm run package` makes `dist/edgebuilder-<version>.zip`) or the `edgebuilder/` folder as a mod and deploy. Releases go through `.github/workflows/release.yml` (REDnode's way): Run workflow in the Actions tab builds the zip as an artifact for the in-game test; with **Make a release** ticked it also makes the GitHub release, with notes from `docs/changelog.md`. Release only after the in-game test of that version passed; never run `gh release create` by hand. No Nexus step until the public preview after B4.
- **Changelog** (the Edgemodders convention, issue #2): `docs/changelog.md`, a section per release `## <version> (<YYYY-MM-DD>)` newest first, `## Unreleased` on top, bold groups **New**, **Changed**, **Fixed**, **Other**, one change per bullet, written for players and modders, full URLs for links. Add the line under Unreleased in the commit that makes the change. Before a release, rename Unreleased to the version and date (the version in `edgebuilder/rednode-app.json` and `package.json`) and start a new empty one. `node tools/release/notes.mjs [version]` prints a section (`--nexus` for plain lines).
- **Data:** scenes live in the REDcode project (`source/scenes/<name>.scene.json`) or, without one, in `pkg.dataDir`; the asset index and settings always in `pkg.dataDir`. Never write into the package folder: hot reload watches it.
