# EDGEbuilder: notes for Claude sessions

EDGEbuilder is a world builder for Cyberpunk 2077 that runs as a REDnode package: pick an asset from the game's own files, drop it into the live game, position it, arrange a scene, bake it into a streaming sector. Read [docs/design.md](docs/design.md) first: the behaviours, the two halves, the pieces, what it needs from the other repos, and the roadmap B0 to B7.

## Picking this up on another machine

The repo is the whole hand-off: there is no state outside it except the player's data folder in the game. Start with this file, then docs/design.md, docs/scene.md and docs/b1-test.md. Sibling checkouts of REDnode (for the SDK source and the mock host), REDbridge (the bridge, 0.6.0 or later) and EDGEdeck make development easier but are not required to build: `npm install`, `npm run build`, `npm run smoke`. With Electron in the REDnode checkout (`node node_modules/electron/install.js` there once), run the host from `<REDnode>/packages/overlay`: `node start.js --render=cpu "--apps-dir=<REDnode>/packages/overlay/apps;<this repo>" --apps=edgebuilder "--data-dir=<scratch folder>"`. `--apps-dir` takes folders whose subfolders are packages, so it is this repo's root, not `edgebuilder/`. Put `{"bridgePath": ..., "gameDir": ...}` in `<scratch folder>/packages/edgebuilder/settings.json` first. Look at the page with the kernel MCP server's `window_image` tool (id `edgebuilder`; token in `<scratch folder>/settings.json`); it works off-screen with `--render=cpu`, not in `--window` mode. To drive the page, start `node_modules/electron/dist/electron.exe --remote-debugging-port=9223 . <same arguments>` from `packages/overlay` (the switch must come before the app path) and evaluate scripts in the page through the DevTools protocol on 127.0.0.1:9223. Done on 2026-10-13: see the B1 test page's results.

## Clean room

The idea comes from World Builder by keanuWheeze (Nexus 20660), a CET mod whose license reserves its code, forks and competing versions. The owner's rule (2026-10-13): study it to understand functionality and which game systems it uses, then write our own from scratch. **Never copy** its Lua, classes, file formats, data lists (its path lists are extracted game data) or archive assets. Design from behaviours and the game API; when a feature looks like it is drifting into World Builder's shapes, stop and redesign.

## Conventions

- **Commits:** commit straight to `main` and push, in small logical commits. Agree the plan in chat first. A PR only for large or risky changes, and ask before opening one.
- **Git identity:** per repo, `CyberbuildsAI` with the GitHub no-reply email. Never change the global identity.
- **Never commit game files** or data extracted from them: archives, meshes, entities, DLLs, the asset index, scenes with the owner's paths. `.gitignore` covers the common cases. The one shipped archive, EDGEbuilder's empty entity, is authored as JSON in this repo and built by REDbridge; the built `.archive` is never committed.
- **House style:** the README with the HUD banner, badges and a status callout; `docs/` rendered by Jekyll with the HUD layout and deployed by `.github/workflows/pages.yml` (Settings > Pages > Source must be GitHub Actions); `tools/brand/` generates the images (`.\tools\brand\render.ps1`, needs Chrome or Edge; `python -I tools/brand/badges.py docs/assets/brand/badges` for the badges alone). REDnode's CLAUDE.md is the canonical source of these idioms.
- **Writing style:** plain, short sentences, tables for comparisons. The behaviours are Browse, Drop, Position, Arrange, Bake, Return; use those words. REDnode's terms: package, overlay app, Node mod, the host, the plugin, `api`.
- **Package layout:** `edgebuilder/` is what deploys; `src/` is TypeScript built into it. `tools/deploy.ps1` mirrors `edgebuilder/` into `<game>\red4ext\plugins\REDnode\apps\edgebuilder` for development (REDnode deployed first, game closed). Players install it with EDGEdeck (0.20.0 and later know the `rednode` kind): add the release zip (`npm run package` makes `dist/EDGEbuilder-<version>.zip` through `tools/release/zip.mjs`, laid out like the game folder, `red4ext/plugins/REDnode/apps/edgebuilder/`, as REDnode's and REDagent's are, so Vortex and an extract by hand work too) or the `edgebuilder/` folder as a mod and deploy. Releases go through `.github/workflows/release.yml` (REDnode's way): Run workflow in the Actions tab builds the zip as an artifact for the in-game test; with **Make a release** ticked it also makes the GitHub release, with notes from `docs/changelog.md`. Release only after the in-game test of that version passed; never run `gh release create` by hand. From the public preview on, the workflow's **Update Nexus Mods** box (with Make a release) uploads the zip to the Nexus page [36627](https://www.nexusmods.com/cyberpunk2077/mods/36627), its changelog and `nexus/description.bbcode`; `nexus/README.md` has the form, the pictures and the steps. The Nexus tool is in EDGErepo (`../EDGErepo/tools/nexus/`; the release workflow clones it at the tag `v1`), since 2026-11-08: change it there. `tools/check-bbcode.mjs` is still REDnode's, copied unchanged: keep it identical and copy it again when REDnode's changes.
- **The wiki at each release (the owner's rule, 2026-11-21, [issue #10](https://github.com/Edgemodders/EDGEbuilder/issues/10); the same in every Edgemodders repo):** right after a release with a version number (the release workflow with **Make a release**, and also for Remove Doors' own releases), in the same piece of work, this session brings EDGEweb's pages about EDGEbuilder up to that version, in the sibling checkout `../EDGEweb`: the wiki section `docs/wiki/edgebuilder/` (Remove Doors' page is `remove-doors.md` there), EDGEbuilder's rows on shared wiki pages (`wiki/library.md` is partly EDGEbuilder's; also `wiki/glossary.md`, `wiki/first-hour.md`, `wiki/faq.md` where they mention it; `grep -rln EDGEbuilder docs` finds the rest), and its card on `docs/index.html` and section on `docs/platform.html`. The version's changelog section is the list of what changed; set each changed page's `reviewed` date; follow EDGEweb's `CLAUDE.md`, Wiki, for front matter, terms and screenshots; commit and push to EDGEweb's `main` as `CyberbuildsAI`, as with the dashboard. The wiki describes what modders can install, not `main`: never change it before the release. It is prose a session writes, so it is a session step, not a workflow step.
- **Changelog** (the Edgemodders convention, issue #2): `docs/changelog.md`, a section per release `## <version> (<YYYY-MM-DD>)` newest first, `## Unreleased` on top, bold groups **New**, **Changed**, **Fixed**, **Other**, one change per bullet, written for players and modders, full URLs for links. Add the line under Unreleased in the commit that makes the change. Before a release, rename Unreleased to the version and date (the version in `edgebuilder/rednode-app.json` and `package.json`) and start a new empty one. `node tools/release/notes.mjs [version]` prints a section (`--nexus` for plain lines).
- **README at each release (the owner's rule, 2026-11-03; the same in every Edgemodders repo):** before a release run, update `README.md`'s status line (`> **Status: <version> released on <date>, for game 2.5; test builds only.**`, then what has shipped and what comes next) and draw the status badge again (`tools/brand/badges.py`: the `status` entry, `"<version> released"`, then `python -I tools/brand/badges.py docs/assets/brand/badges`; the README's `<img alt>` too). The version is the one in `edgebuilder/rednode-app.json` and `package.json`. The release workflow stops before building when they do not say it (`tools/release/readme-check.mjs`, a copy of REDnode's kept identical: copy it again from REDnode when it changes there, never edit it here). The badge said "B2b passed" and its alt "design, B0" through 0.5.8 before this rule.
- **Data:** scenes live in the REDcode project (`source/scenes/<name>.scene.json`) or, without one, in `pkg.dataDir`; the asset index and settings always in `pkg.dataDir`. Never write into the package folder: hot reload watches it.

## Docs site

- `docs/` is published at https://edgemodders.github.io/EDGEbuilder/. `index.md` is the landing page with the document ledger and the roadmap status table; keep that table current with every phase.
- `docs/design.md` is the design; bump its draft number when it changes materially. Results pages per phase go beside it and into the ledger and `nav` in `docs/_config.yml`.

## Dashboard (EDGEweb)

The platform dashboard at https://edgemodders.ai/dashboard.html draws one file in the EDGEweb repo, `docs/assets/dashboard/status.js` (plain JSON after the equals sign, one object per tool under `tools`). The owner and a managing session read it to see every tool's state, so EDGEbuilder's entry is kept current by the session that works on EDGEbuilder.

- **When:** in the same piece of work as any change to EDGEbuilder's status: a phase built or done, a hand test added, run, passed or failed, a release, something EDGEbuilder starts or stops waiting on, something only the owner can do.
- **How:** in the sibling checkout `../EDGEweb`, `git pull`, edit only EDGEbuilder's object, set its `checkedBy` to this session and the date, bump the `?v=` on the `status.js` script tag in `docs/dashboard.html`, commit and push to `main` (as `CyberbuildsAI`). Leave `issues`, `lastTag`, `lastTagDate`, `lastCommit` and `commitsSinceTag` alone: EDGEweb's `tools/dashboard/refresh.py` writes those.
- **Words:** phases are `done`, `built, tests pending`, `in progress` or `planned`; tests are `passed`, `not run`, `partly run` or `failed`. The fields are described in EDGEweb's `CLAUDE.md`, under Dashboard.
- **Honest:** never mark a test passed or a phase done that this repo's own docs do not. A test with a step still to run is `partly run`.
